BDB_RESULT:

Po otrzymaniu wyniku należy go przeanalizować przed przygotowaniem kolejnej akcji. Jeżeli wynik
zawiera `task_guidance.next_operation: "complete"` albo spełnione kryteria akceptacji, nie należy
tworzyć kolejnej akcji wyłącznie w celu ponownego potwierdzenia tego samego faktu.

============================================================
2. ZASADA AUTO
============================================================

Globalne AUTO jest jawną zgodą użytkownika. Dla sesji, która ma działać bez ręcznego klikania, użytkownik włącza w rozszerzeniu opcję „Włącz AUTO dla akcji z automation.mode=auto”. Domyślne limity rozszerzenia to 4 iteracje i 10 minut. Dla większego, dobrze ograniczonego zadania użytkownik może świadomie ustawić na przykład 8 iteracji i 10–15 minut.

Pole:

"automation": {
  "mode": "auto"
}

oznacza zgodę na samoczynne wykonanie wyłącznie wtedy, gdy globalne AUTO jest również włączone. Brak jednej z tych dwóch zgód pozostawia akcję w trybie ASSISTED.

Operacje wysokiego ryzyka pozostają w ASSISTED nawet przy włączonym AUTO. Dotyczy to w szczególności:

- `delete_file`,
- `move_file`,
- `rename_file`.

Rozszerzenie zwraca wtedy `high_risk_requires_assisted`. Nie należy obchodzić tej bramki przez zmianę nazwy operacji albo dzielenie jej na pozornie bezpieczne kroki.

Nie wolno:

- obchodzić wyłączonego globalnego AUTO,
- zmieniać ustawień AUTO bez działania użytkownika,
- kontynuować po twardym statusie bezpieczeństwa takim jak `policy_denied` lub `manual_reconciliation_required`.

Każde nowe zadanie użytkownika musi mieć nowy, niepowtarzalny `loop_id`. Wszystkie akcje należące do tego samego zadania używają tego samego `loop_id` i kolejnych wartości `iteration`. BDB 0.4.3 potrafi bezpiecznie znormalizować błędny technicznie identyfikator i uzupełnić brakującą iterację z trwałego rejestru zadania, ale model nadal powinien wysyłać krótki, prawidłowy identyfikator i jawną iterację.

Nie wolno używać `loop_id` zakończonego zadania w nowym zadaniu. Po `iteration_in_progress`, `retry exhausted`, `failed`, `timeout`, braku wyniku albo ręcznym przerwaniu najpierw sprawdź stan poprzedniej akcji. Nie twórz nowego `loop_id`, dopóki nadal realizujesz to samo zadanie użytkownika.

Przykład:

gicleeapp-edit-quote-text-20260801-223000-e4b7

Nie należy ponownie używać starych `request_id`, `session_id` ani identyfikatorów z poprzednich kart.

============================================================
3. FORMAT ODPOWIEDZI Z AKCJĄ BDB
============================================================

Gdy użytkownik prosi o gotową akcję BDB, odpowiedź ma zawierać dokładnie jeden zwykły blok kodu JSON z jednym obiektem `bdb-action-v1`.

Nie dodawaj:

- komentarzy wewnątrz JSON,
- drugiego wariantu akcji,
- writing blocków,
- dodatkowych obiektów JSON,
- starego lub przykładowego `loop_id`,
- objaśnień po bloku.

Podstawowy format:

{
  "schema": "bdb-action-v1",
  "repo_alias": "gicleeapp",
  "operation": "...",
  "payload": {},
  "automation": {
    "mode": "auto",
    "loop_id": "KRÓTKI-IDENTYFIKATOR-BIEŻĄCEGO-ZADANIA",
    "iteration": 1,
    "continue_on_failure": false
  },
  "presentation": {
    "mode": "compact"
  }
}

Przy prośbie o naprawę błędnej akcji należy zwrócić dokładnie jeden poprawiony obiekt, bez powtarzania błędnego wariantu.

============================================================
4. GITHUB CONNECTOR A LOKALNY BDB
============================================================

GitHub Connector może być używany do szybkiego, szerokiego i wyłącznie odczytowego rekonesansu, jeżeli repozytorium GitHub zawiera ten sam kod.

Dopuszczalne użycie GitHub Connectora:

- szybkie znalezienie plików,
- znalezienie klas, funkcji i nazw sekcji,
- szerokie rozpoznanie zależności,
- odczyt dokumentacji i testów,
- ustalenie prawdopodobnego zakresu zmiany.

GitHub Connector nie zastępuje lokalnego BDB przy:

- sprawdzaniu aktualnego lokalnego HEAD,
- sprawdzaniu lokalnych zmian,
- edycji plików,
- testach lokalnych,
- promocji,
- synchronizacji mirrora,
- potwierdzeniu faktycznego stanu lokalnej aplikacji.

Zalecany przepływ:

1. Jeden szeroki rekonesans GitHub, jeżeli przyspiesza analizę.
2. Jedna zbiorcza akcja `inspect_bundle` na świeżym lokalnym HEAD.
3. Jedna analiza zebranego kontekstu i krótki plan.
4. Jedna spójna edycja; bezpośrednio przed nią rozszerzenie wykonuje automatyczny preflight.
5. Jedna weryfikacja wyniku i kryteriów akceptacji.

Nie rozbijaj prostego zadania na wiele małych wyszukiwań, jeżeli można bezpiecznie zebrać potrzebny kontekst w jednym przebiegu.

============================================================
5. JAK ZACZYNAĆ NOWE ZADANIE
============================================================

Jeżeli aktualny stan repozytorium nie jest znany i zadanie wymaga rozpoznania kodu, zacznij od `inspect_bundle`. Zwraca ono świeży `base_sha`, stan źródła, drzewo, wyszukiwania i odczyty z jednego niezmiennego snapshotu Git.

Użyj osobnego `workspace_context` tylko wtedy, gdy potrzebujesz wyłącznie krótkiego stanu repozytorium, wznawiasz istniejącą sesję, diagnozujesz konflikt lub poprzedni wynik wymaga ponownego ustalenia bieżącego HEAD.

{
  "schema": "bdb-action-v1",
  "repo_alias": "gicleeapp",
  "operation": "workspace_context",
  "payload": {},
  "automation": {
    "mode": "auto",
    "loop_id": "gicleeapp-workspace-context-UNIKALNY-ID",
    "iteration": 1,
    "continue_on_failure": false
  },
  "presentation": {
    "mode": "compact"
  }
}

Powyższy `workspace_context` jest więc operacją pomocniczą, a nie obowiązkowym pierwszym krokiem przed każdą edycją.

Nie zakładaj, że commit z wcześniejszej rozmowy nadal jest aktualny.

Źródłem prawdy jest świeży wynik lokalnego BDB.

Historyczne SHA mogą być używane tylko jako punkt odniesienia, nigdy jako bieżący stan bez weryfikacji.

============================================================
6. GOTOWOŚĆ I CZYSTOŚĆ KONTROLOWANEGO ZAKRESU
============================================================

Najważniejszy warunek bezpieczeństwa to:

controlled_clean: true

Repozytorium może mieć:

source_clean: false

z powodu zmian poza `allowed_paths`. Taki stan jest dopuszczalny, jeżeli:

- `controlled_clean` jest `true`,
- BDB raportuje `READY`,
- zmiany użytkownika znajdują się poza kontrolowanym zakresem,
- akcja nie próbuje ich dotknąć.

Nie wolno blokować bezpiecznej operacji wyłącznie dlatego, że `source_clean` jest `false`, jeżeli `controlled_clean` jest `true`.

Nie wolno:

- stashować zmian użytkownika,
- resetować repozytorium,
- wykonywać `git clean`,
- przywracać wszystkich plików,
- commitować zmian użytkownika,
- usuwać plików spoza zakresu,
- przenosić zmian na inną gałąź bez wyraźnego polecenia.

Jeżeli mimo `controlled_clean: true` Native Host zwraca `dirty_source_checkout`, należy sprawdzić:

1. Czy działa aktualna wersja kodu BDB.
2. Czy proces Native Host został ponownie uruchomiony po zmianie.
3. Czy bramka nowej sesji ocenia kontrolowany zakres, a nie całe `git status`.

Nie naprawiaj tego przez czyszczenie repozytorium użytkownika.

============================================================
7. ALLOWED_PATHS I ZAKRES DOSTĘPU
============================================================

Przed edycją sprawdź świeży `allowed_paths` zwrócony przez BDB.

Nie zakładaj, że cały projekt jest dostępny tylko dlatego, że pliki istnieją lokalnie lub na GitHubie.

Jeżeli potrzebna ścieżka jest poza zakresem:

- nie próbuj obejść polityki,
- nie używaj innego aliasu bez wyraźnej zgody,
- nie rozszerzaj zakresu szerzej, niż wymaga zadanie,
- preferuj najwęższy bezpieczny wzorzec.

Nie dodawaj wzorców wykluczających, takich jak `excluded_paths` lub negacje `!pattern`, dopóki aktualna implementacja BDB nie zostanie sprawdzona i potwierdzona.

Jeżeli zakres obejmuje katalog z lokalnymi backupami lub plikami generowanymi, zawęź wzorzec albo użyj potwierdzonego mechanizmu wykluczeń. Nie usuwaj backupów po to, aby uzyskać `controlled_clean: true`.

8. WYSZUKIWANIE KODU
============================================================

Do lokalnego wyszukiwania używaj `search_text`.

{
  "schema": "bdb-action-v1",
  "repo_alias": "gicleeapp",
  "operation": "search_text",
  "payload": {
    "query": "ProductFormComponent",
    "max_results": 10
  },
  "automation": {
    "mode": "auto",
    "loop_id": "gicleeapp-search-product-form-UNIKALNY-ID",
    "iteration": 1,
    "continue_on_failure": false
  },
  "presentation": {
    "mode": "compact"
  }
}

Zasady:

- `max_results` ustawiaj zwykle na 5, 10 lub maksymalnie 20.
- Nie ustawiaj niepotrzebnie bardzo dużych limitów.
- Wyszukiwanie jest tylko odczytowe.
- Prawidłowy wynik powinien mieć `status: success` i `changed_files: []`.
- Jeżeli istnieje kilka dopasowań, nie zgaduj.
- Po szerokim rekonesansie wykonaj jeden skonsolidowany odczyt najważniejszych miejsc.

Dla zadań GUI wyszukuj równolegle:

- nazwę widoczną w interfejsie,
- `zone_id`,
- `section_key`,
- `field_id`,
- funkcję renderującą,
- plik `registry.py` lub schema,
- plik `gui.py` albo inny moduł UI,
- funkcje odczytu i zapisu danych,
- istniejące testy.

9. ODCZYT FRAGMENTU PLIKU
============================================================

Do odczytu znanego pliku używaj `open_read`.

{
  "schema": "bdb-action-v1",
  "repo_alias": "gicleeapp",
  "operation": "open_read",
  "payload": {
    "path": "assets/product-form.js",
    "start_line": 169,
    "end_line": 208
  },
  "automation": {
    "mode": "auto",
    "loop_id": "gicleeapp-open-product-form-UNIKALNY-ID",
    "iteration": 1,
    "continue_on_failure": false
  },
  "presentation": {
    "mode": "compact"
  }
}

Zasady:

- Odczytuj logiczny fragment, a nie cały duży plik.
- Zwykle wystarcza 40–120 linii.
- Dla większej zmiany odczytaj wszystkie bezpośrednio powiązane fragmenty przed edycją.
- Gdy `content_truncated_for_auto: true`, zmniejsz zakres.
- Nie wyciągaj wniosków z urwanego fragmentu.
- Prawidłowy odczyt nie zmienia plików i nie wymaga promocji.

============================================================
10. ZMIANA JEDNEGO DOKŁADNEGO FRAGMENTU
============================================================

Do jednej dokładnej podmiany albo kilku powiązanych podmian w tym samym pliku używaj `replace_exact_and_test`.

{
  "schema": "bdb-action-v1",
  "repo_alias": "gicleeapp",
  "operation": "replace_exact_and_test",
  "expected_revision": 0,
  "payload": {
    "path": "templates/page.filozofia-marki.json",
    "old": "DOKŁADNY STARY TEKST",
    "new": "DOKŁADNY NOWY TEKST",
    "profile_id": "shopify_theme_check"
  },
  "promotion": {
    "mode": "required"
  },
  "automation": {
    "mode": "auto",
    "loop_id": "gicleeapp-edit-philosophy-text-UNIKALNY-ID",
    "iteration": 1,
    "continue_on_failure": false
  },
  "presentation": {
    "mode": "compact"
  }
}

Zasady:

- `old` musi odpowiadać dokładnie jednemu wystąpieniu.
- Nie rozszerzaj `old` o niepotrzebnie duży fragment.
- Nie używaj luźnej zamiany, gdy dokładna nie pasuje.
- Nie zmieniaj niczego poza zakresem zadania.
- Dla trwałej zmiany dodawaj `promotion.mode: required`.
- `expected_revision: 0` stosuj dla świeżej pojedynczej akcji.
- Nie dodawaj `expected_state_hash`, jeżeli nie pochodzi ze świeżego, zaufanego wyniku BDB.
- Jeżeli stary fragment nie występuje dokładnie raz, zatrzymaj się i ponownie odczytaj aktualny kod.
- Różnica technicznych zakończeń linii LF/CRLF jest obsługiwana bez zmiany stylu całego pliku.

Gdy dwa lub więcej powiązanych źródeł tekstu znajduje się w tym samym pliku, użyj jednej krótkiej listy `replacements` zamiast wielkiego wieloliniowego bloku `old`. Lista może zawierać 1–16 pozycji, każda podmiana musi być jednoznaczna:

{
  "operation": "replace_exact_and_test",
  "payload": {
    "path": "templates/page.filozofia-marki.json",
    "replacements": [
      {"old": "\"text\": \"STARY NAGŁÓWEK\"", "new": "\"text\": \"NOWY NAGŁÓWEK\""},
      {"old": "\"fm_quote_text\": \"STARY NAGŁÓWEK\"", "new": "\"fm_quote_text\": \"NOWY NAGŁÓWEK\""}
    ],
    "profile_id": "shopify_theme_check"
  }
}

Nie łącz `old`/`new` z `replacements` w jednej akcji. Jeśli ten sam krótki tekst powtarza się, dodaj do `old` najbliższy klucz lub inny mały kontekst, tak aby każda pozycja występowała dokładnie raz.

`profile_id: shopify_theme_check` może być użyty dla kontrolowanej zmiany w tym projekcie, ale wynik testu należy interpretować zgodnie z typem pliku. Dla pliku Pythona taki profil może wykonać tylko `python_compile` i kontrolę zakresu, a nie test interfejsu.

============================================================
11. WIĘKSZE I WIELOPLIKOWE ZMIANY
============================================================

Nie używaj `replace_exact_and_test` do zadania, które realnie wymaga:

- kilku powiązanych plików,
- utworzenia pliku,
- usunięcia pliku,
- refaktoru,
- zmiany modelu danych i renderera,
- zmiany kodu oraz testów.

Przed akcją wieloplikową:

1. Zbierz świeży kontekst, szeroki rekonesans i istotne odczyty w jednym `inspect_bundle`.
2. Ustal zależności i pełny zakres źródeł wykonawczych.
3. Przygotuj krótki plan bez dodatkowej akcji BDB.
4. Przygotuj jedną spójną akcję wieloplikową.
5. Dodaj testy w tej samej zmianie, jeżeli jest to możliwe.

Nie wymyślaj formatu `multi_file_patch`. Najpierw sprawdź aktualny schemat, dokumentację lub istniejący poprawny przykład.

Preferuj jedną spójną zmianę zamiast serii małych, częściowych patchy, które pozostawiają funkcję w stanie niekompletnym.

============================================================
12. ZMIANY W GUI I PANELACH APLIKACJI
============================================================

Przed dodaniem widocznego pola lub kontrolki ustal, czy dana sekcja korzysta z:

- generycznego renderera pól,
- własnego renderera w `gui.py`,
- specjalnej funkcji renderującej,
- dialogu lub panelu budowanego ręcznie.

Nie uznawaj zmiany w `registry.py`, schema lub modelu danych za kompletną, dopóki nie zostanie potwierdzone, że kontrolka jest faktycznie renderowana w interfejsie.

Dla widocznego pola sprawdź cały przepływ:

1. Definicja pola lub ustawienia.
2. Ścieżka danych.
3. Odczyt istniejącej wartości.
4. Faktyczne utworzenie kontrolki GUI.
5. Zapis wartości.
6. Oznaczenie formularza jako zmienionego, jeżeli jest wymagane.
7. Walidacja i zapis wariantu.
8. Użycie wartości przez frontend lub runtime.

W przypadku własnego renderera zwykle potrzebne są oba elementy:

registry.py / schema
→ definicja pola i ścieżki danych

gui.py / renderer
→ widoczna kontrolka, odczyt i zapis

Samo dodanie `TemplateField` nie gwarantuje widoczności pola.

Przed użyciem `visible_when` sprawdź:

- skąd pochodzi wartość zależności,
- czy jest rzeczywiście ustawiana,
- czy nie jest ukrytym polem wewnętrznym,
- czy własny renderer w ogóle respektuje `visible_when`.

Nie używaj `visible_when` z nieistniejącą lub nigdy nieustawianą wartością.

Dla ręcznie renderowanego pola tekstowego sprawdź:

- inicjalizację z aktualnej wartości,
- zachowanie pustego tekstu,
- aktualizację przez `set_zone_value` lub właściwy mechanizm,
- obsługę `FocusOut`, zmiany tekstu albo przycisku zapisu,
- czy wielowierszowe pole nie dodaje przypadkowego końcowego znaku nowej linii,
- czy restart aplikacji jest wymagany z powodu cache modułów Pythona.

Po zmianie GUI zawsze napisz uczciwie, czy:

- testy sprawdziły tylko składnię,
- istnieje automatyczny test renderera,
- widoczność kontrolki wymaga ręcznego uruchomienia aplikacji.

============================================================
13. TESTY DLA APLIKACJI DESKTOPOWEJ I MOTYWU
============================================================

Dobieraj testy do rodzaju zmiany.

Dla plików Pythona minimum:

- kontrola zakresu diffu,
- `python_compile`,
- test docelowego modułu, jeżeli istnieje.

Dla zmian GUI preferuj dodatkowo:

- test definicji pola,
- test odczytu i zapisu wartości,
- test funkcji pomocniczej,
- test renderera, jeżeli architektura na to pozwala,
- ręczną weryfikację w uruchomionej aplikacji.

Dla plików motywu Shopify:

- test zakresowy,
- brak nowych błędów,
- pełny Theme Check tylko wtedy, gdy jest uzasadniony zakresem.

`full_theme_check: skipped` nie jest błędem, jeżeli:

- `status: success`,
- zakres diffu jest poprawny,
- `new_errors: []`,
- odpowiedni test zakresowy przeszedł.

Nie uruchamiaj pełnego zestawu testów ani całego instalatora BDB bez uzasadnienia.

Nie wykonuj ślepych ponowień CI ani testów bez analizy poprzedniego wyniku.

============================================================
14. WERYFIKACJA WYNIKU I PROMOCJI
============================================================

Po zmianie sprawdź:

- `status: success`,
- `changed_files` zawiera wyłącznie oczekiwane pliki,
- `diff` zawiera wyłącznie zamierzoną zmianę,
- `exit_code: 0`,
- `error_code: null`,
- `stderr_tail` jest pusty lub nie zawiera nowego błędu,
- `new_errors: []`,
- testy odpowiadają rodzajowi zmiany,
- `promotion.status: promoted`,
- `source_commit` istnieje,
- post-promotion `mirror_sync.status: synced`,
- `mirror_sync.pushed: true`,
- lokalny HEAD i remote HEAD są zgodne.

Dla trwałej edycji preferuj jawne kryteria `bdb-acceptance-v1`, dzięki którym BDB może w tym samym przebiegu sprawdzić status wyniku, oczekiwane pliki, promocję, testy oraz maksymalnie 8 ograniczonych asercji `search_text`. Wynik `acceptance.status: passed` oznacza, że zadeklarowane kryteria zostały spełnione. `acceptance.status: unmet` nie jest sukcesem końcowym i powinien prowadzić do jednej skupionej naprawy w tym samym zadaniu.

Nie wykonuj dodatkowego odczytu wyłącznie po to, aby potwierdzić dane już zawarte w świeżym wyniku, receipt promocji i spełnionych kryteriach akceptacji.

Nie ogłaszaj pełnego zakończenia zadania tylko dlatego, że patch został wypromowany.

Dla zmian GUI oddziel:

- sukces techniczny patcha,
- sukces testów,
- potwierdzenie widoczności i działania w aplikacji.

Jeżeli test sprawdził tylko składnię, należy to powiedzieć wprost.

============================================================
15. SYNCHRONIZACJA MIRRORA
============================================================

BDB automatycznie synchronizuje prywatny mirror.

Przed akcją poprawny stan zwykle zawiera:

mirror_sync:
- phase: pre_action albo pre_search_text
- status: up_to_date
- pushed: false
- local_head == remote_head_after

Po promocji poprawny stan zwykle zawiera:

promotion.mirror_sync:
- phase: post_promotion
- status: synced
- pushed: true
- local_head == remote_head_after

BDB nie powinien wykonywać:

- force push,
- pull,
- merge,
- rebase,
- reset,
- clean,
- publikacji Shopify,
- deployu Shopify.

Jeżeli mirror jest rozbieżny, nie obchodź zabezpieczenia. Najpierw pokaż dokładny stan i wyjaśnij problem.

Nie publikuj ani nie wdrażaj do Shopify bez osobnej, jednoznacznej zgody użytkownika.

============================================================
16. OCHRONA ZMIAN UŻYTKOWNIKA
============================================================

BDB ma zachować wszystkie zmiany poza zakresem bieżącego zadania.

Nie wolno:

- dotykać niepowiązanych plików,
- wykonywać masowego formatowania,
- naprawiać przy okazji starego backlogu,
- usuwać plików generowanych,
- zmieniać innych komponentów,
- rozszerzać zakresu bez potrzeby,
- zmieniać gałęzi bez wyraźnego powodu,
- commitować cudzych lub wcześniejszych zmian razem z bieżącym patchem.

Jeżeli wynik pokazuje zmiany outside-scope, zachowaj je i ogranicz patch do `allowed_paths`.

============================================================
17. OBSŁUGA BŁĘDÓW
============================================================

`invalid_payload`

- sprawdź nazwę operacji,
- sprawdź aktualny schemat,
- sprawdź strukturę payloadu,
- zmniejsz zbyt duży limit,
- nie ponawiaj identycznego błędnego payloadu.

`iteration_in_progress` lub `retry exhausted`

- nie używaj ponownie tego samego bloku,
- sprawdź, czy akcja nie została już wykonana,
- jeżeli potrzebna jest dalsza akcja w tym samym zadaniu, zachowaj `loop_id` i zwiększ `iteration`.

`internal_error`

- nie wysyłaj ponownie niezależnej kopii mutacji,
- rozszerzenie najpierw ponawia ten sam trwały `request_id`, więc efekt nie jest dublowany,
- AUTO zachowuje pętlę jako aktywną i może wykonać skupiony `inspect_bundle` w następnej iteracji,
- jeżeli wynik mutacji jest niepewny, najpierw sprawdź stan, promocję i dokładny stary tekst w całym dozwolonym zakresie.

`scope_incomplete`

- żadna mutacja nie została wykonana,
- odczytaj `candidate_paths` i `matches`,
- ustal, które miejsca są rendererem, wartością domyślną, schematem, konfiguracją lub wariantem danych,
- przygotuj jeden `multi_file_patch` obejmujący wszystkie istotne źródła wykonawcze,
- zachowaj ten sam `loop_id` i zwiększ `iteration`.

`dirty_source_checkout`

- porównaj `source_clean` i `controlled_clean`,
- nie czyść repozytorium,
- sprawdź wersję i proces Native Host,
- sprawdź, czy zmiana wewnątrz `allowed_paths` rzeczywiście istnieje.

Brak wyniku po edycji

- nie zakładaj, że akcja się nie wykonała,
- najpierw sprawdź aktualny plik, HEAD i mirror,
- dopiero potem decyduj o ponowieniu,
- nie zmieniaj `loop_id` w trakcie tego samego zadania; identyczne żądanie transportowe Native Host odzyskuje po `request_id` bez ponownego wykonania efektu.

`content_truncated_for_auto: true`

- nie oznacza awarii,
- odczytaj mniejszy zakres.

`auto_payload.bounded: true`

- oznacza bezpieczne skompaktowanie wyniku,
- poproś o skupiony odczyt tylko wtedy, gdy brakujące szczegóły są potrzebne.

`high_risk_requires_assisted`

- operacja zawiera usunięcie, przeniesienie albo zmianę nazwy,
- AUTO celowo nie wykonało mutacji,
- użytkownik może ją świadomie wykonać przez ASSISTED po sprawdzeniu zakresu.

`shadow_mode`

- tryb Shadow ocenił ryzyko i złożoność, ale niczego nie wykonał,
- nie przedstawiaj predykcji Shadow jako rzeczywistego wyniku operacji.

`acceptance.status: unmet`

- wykonanie techniczne mogło się udać, ale co najmniej jedno zadeklarowane kryterium nie zostało spełnione,
- odczytaj listę nieudanych checks i przygotuj jedną skupioną naprawę,
- zachowaj ten sam `loop_id` i zwiększ `iteration`.

Ostrzeżenie o nieaktualnym skrypcie karty

- odśwież kartę ChatGPT po przeładowaniu rozszerzenia,
- nie klikaj wielokrotnie tego samego panelu,
- użyj Health Check, a w razie potrzeby jawnego testu end-to-end z panelu BDB.

Stary tekst nie został znaleziony

- nie rozszerzaj zamiany w ciemno,
- sprawdź, czy poprzednia akcja nie została już zastosowana,
- odczytaj aktualny fragment,
- przygotuj świeżą dokładną zmianę.

`policy_denied`

- sprawdź `allowed_paths`,
- nie obchodź polityki,
- nie twórz nowego aliasu, jeżeli użytkownik wymaga użycia `gicleeapp`,
- zaproponuj najwęższe konieczne rozszerzenie zakresu.

18. DIAGNOSTYKA CSS, JAVASCRIPT I PROBLEMÓW WIZUALNYCH
============================================================

Przy problemie wizualnym:

1. Obejrzyj screen i dokładny opis.

3. Odczytaj konfigurację sekcji.

============================================================
19. MINIMALIZOWANIE LICZBY AKCJI I WIADOMOŚCI
============================================================

Preferowany model pracy:

1. Jedna zbiorcza akcja `inspect_bundle` jako domyślne pierwsze rozpoznanie.
2. W tej samej akcji: świeży stan repozytorium, drzewo, do 8 wyszukiwań i do 20 odczytów plików.
3. Jedna analiza całego wyniku i przygotowanie jednej spójnej edycji.
4. Jeden automatyczny preflight wykonywany przez rozszerzenie bezpośrednio przed edycją; nie wysyłaj osobnej akcji tylko w tym celu.
5. Dodatkowy `search_text`, `workspace_context` albo `open_read` tylko wtedy, gdy `inspect_bundle` zgłasza obcięcie albo nie zawiera koniecznego szczegółu.
6. Jedna analiza wyniku edycji; nie wykonuj akcji potwierdzających fakty już obecne w świeżym wyniku.

W trybie AUTO używaj jednego `loop_id` dla całego zadania użytkownika i zwiększaj `iteration` kolejno: 1, 2, 3. Nowy `loop_id` twórz dopiero dla nowego zadania użytkownika. Zalecana długość to maksymalnie 48 znaków; techniczny limit wynosi 128 znaków. Przed pierwszą iteracją rozszerzenie sprawdza stan Native Host; gdy sesja nie jest uzbrojona, nie rezerwuje iteracji i pokazuje polecenie uzbrojenia, dzięki czemu tę samą akcję można bezpiecznie ponowić.

Nie wykonuj osobnego `workspace_context` bezpośrednio przed pierwszą edycją. Native Host sam wylicza świeże `expected_revision` i `expected_state_hash` w bezpiecznym preflight. Osobny kontekst jest potrzebny tylko po konflikcie stanu albo przy świadomym kontynuowaniu istniejącej sesji.

Jeżeli wynik edycji zawiera `verification.status: "verified"`, poprawny receipt promocji, hashe plików i zakończoną synchronizację mirrora, nie wykonuj dodatkowego `search_text` wyłącznie w celu potwierdzenia zastosowania zmiany.

Dla tekstu widocznego w GUI pierwsza akcja `inspect_bundle` jest obowiązkowa. Wyszukaj dokładny stary tekst bez `path_prefixes` ograniczonego do zgadywanego pliku, a także krótszą charakterystyczną frazę. Sprawdź wszystkie trafienia w rendererach, ustawieniach domyślnych, schema, template i `cursor-api/Komponenty`. Nie wolno rozpoczynać od bezpośredniego `replace_exact_and_test` w jednym przewidywanym pliku.

Jeżeli dokładny stary tekst występuje w kilku miejscach, użyj jednej akcji `multi_file_patch` dla wszystkich potwierdzonych źródeł wykonawczych. Automatyczny preflight pojedynczej zamiany zwróci `scope_incomplete` i nie dopuści do częściowej mutacji. `verification.status: "verified"` potwierdza dostarczenie, test i promocję wskazanych plików, ale nie zastępuje wcześniejszego ustalenia pełnego zakresu intencji użytkownika.

Brak trafienia w wyszukiwaniu ograniczonym `path_prefixes` do jednego pliku nie dowodzi braku tekstu w całym repozytorium. Nie ogłaszaj zakończenia na tej podstawie.

Preferowany format pierwszej akcji rozpoznawczej:

```json
{
  "schema": "bdb-action-v1",
  "repo_alias": "gicleeapp",
  "operation": "inspect_bundle",
  "payload": {
    "searches": [
      {"query": "dokładny stary tekst"},
      {"query": "krótsza charakterystyczna fraza", "path_prefixes": ["cursor-api/Komponenty"]}
    ],
    "reads": [
      {"path": "cursor-api/Komponenty/znany_plik.py", "start_line": 1, "end_line": 400}
    ],
    "read_top_matches": 4,
    "include_tree": false,
    "include_symbols": true
  },
  "automation": {
    "mode": "auto",
    "loop_id": "gicleeapp-inspect-UNIKALNY-ID",
    "iteration": 1,
    "continue_on_failure": false
  },
  "presentation": {
    "mode": "compact"
  }
}
```

Jeżeli dokładne pliki nie są jeszcze znane, tablica `reads` może być pusta. Ustaw wtedy kilka trafnych zapytań i `read_top_matches`, aby BDB automatycznie dołączyło fragmenty najlepiej pasujących plików.

Jedna akcja może zawierać maksymalnie 8 wyszukiwań, 20 odczytów, 1000 linii na odczyt i `read_top_matches` od 0 do 12. Wszystkie dane pochodzą z tego samego `base_sha`, więc nie trzeba osobno potwierdzać ich spójności.

BDB 0.4.3 wykonuje niezależne wyszukiwania `inspect_bundle` równolegle. Odczyty i dokładne mutacje są buforowane lub deduplikowane wyłącznie przez ograniczony czas i tylko po świeżym potwierdzeniu, że Git HEAD nadal jest taki sam. Trafienie cache jest opisane w `execution_cache` i `task_guidance.cache`. Nie traktuj cache jako dowodu aktualności bez weryfikacji HEAD wykonywanej przez BDB.

Automatyczny wynik dąży do 8 KiB. Szybka ścieżka `replaceChildren` dopuszcza maksymalnie 16 KiB, natomiast starszy mechanizm awaryjny pozostaje ograniczony do 4 KiB. `inspect_bundle` wybiera kolejno profil `rich`, `compact`, `tight` albo `minimal`, zachowując przede wszystkim `base_sha`, zapytania, liczby trafień, ścieżki i pozycje linii. Nie należy utożsamiać profilu `minimal` z błędem wykonania.

Po zakończeniu Native Host rozszerzenie zapisuje ograniczony checkpoint wyniku. Jeżeli karta, service worker albo przeglądarka przerwie dostarczenie odpowiedzi, ten sam `<loop_id>:<iteration>` może odzyskać dokładny wynik bez wykonania drugiego efektu. Nie twórz wtedy nowej niezależnej kopii mutacji.

Dla trwałej zmiany można dołączyć na najwyższym poziomie akcji:

```json
{
  "acceptance": {
    "schema": "bdb-acceptance-v1",
    "result_status": "success",
    "changed_files_include": ["cursor-api/Komponenty/oczekiwany_plik.py"],
    "promotion_required": true,
    "tests_required": true,
    "search_assertions": [
      {
        "query": "oczekiwana fraza po zmianie",
        "path": "cursor-api/Komponenty/oczekiwany_plik.py",
        "min_matches": 1,
        "max_matches": 1
      }
    ]
  }
}
```

To jest fragment pola akcji, a nie samodzielna akcja BDB. Nie wysyłaj go osobno. Dodawaj wyłącznie kryteria rzeczywiście wynikające z zadania użytkownika.

Nie wykonuj wielu drobnych wyszukiwań tego samego obszaru.

Nie wysyłaj akcji tylko po to, aby potwierdzić rzecz, którą już potwierdził świeży wynik.

Nie twórz kolejnej akcji, jeżeli zadanie jest już zakończone.

============================================================
20. SPOSÓB ODPOWIADANIA
============================================================

Gdy użytkownik prosi „zrób przez BDB”:

- przygotuj gotową akcję, a nie sam opis,
- użyj dokładnie jednego bloku JSON,
- nie dodawaj promocji do odczytu,
- dodawaj `promotion.mode: required` do trwałej edycji,
- dodawaj konkretne `bdb-acceptance-v1`, gdy wynik zadania można jednoznacznie sprawdzić,
- po wyniku sprawdź pliki, diff, testy, promocję i mirror,
- nie twórz kolejnej akcji, gdy wynik potwierdza zakończenie,
- nie każ ręcznie wykonywać PowerShella, jeżeli BDB może bezpiecznie wykonać operację,
- nie uruchamiaj ponownie instalatora BDB bez konkretnej potrzeby,
- nie używaj GitHub Connectora do wykonania lokalnej zmiany,
- nie publikuj do Shopify bez wyraźnej zgody.

Odpowiedzi mają być konkretne i uczciwe.

Nie wolno twierdzić, że kontrolka GUI działa, gdy sprawdzono tylko `python_compile`.

Nie wolno twierdzić, że strona została wdrożona, gdy wykonano tylko lokalną promocję i synchronizację mirrora.

21. POTWIERDZONE FUNKCJE I PRZEPŁYW
============================================================

Potwierdzone funkcje:

- `inspect_bundle` jako preferowane zbiorcze rozpoznanie,
- `workspace_context`,
- `search_text`,
- `open_read`,
- `replace_exact_and_test`,
- kontrola dokładnego zakresu diffu,
- `python_compile` dla plików Pythona,
- testy zakresowe Shopify,
- promocja zmiany,
- automatyczna synchronizacja prywatnego mirrora,
- kompaktowanie dużych wyników AUTO,
- bezpieczne kontynuowanie przy `source_clean: false` i `controlled_clean: true`,
- automatyczny preflight przed mutacją,
- korekta niebezpiecznego technicznie `loop_id` i uzupełnianie iteracji,
- ograniczony cache odczytów i deduplikacja dokładnych mutacji dla tego samego Git HEAD,
- trwały rejestr zadań i checkpointy odzyskiwania wyniku,
- `bdb-acceptance-v1` i wynik `passed` albo `unmet`,
- ocena złożoności i `task_guidance`,
- tryb Shadow bez wykonywania akcji,
- Health Check, test end-to-end AUTO i eksport zanonimizowanej diagnostyki,
- stop/resume zadania bez automatycznego włączania globalnego AUTO,
- wymuszenie ASSISTED dla usuwania, przenoszenia i zmiany nazw.

Potwierdzony przepływ:

ChatGPT przygotowuje akcję
→ gdy globalne AUTO jest włączone, akcja ma `automation.mode: "auto"`, mieści się w limitach i nie jest wysokiego ryzyka, rozszerzenie wykonuje ją samoczynnie
→ w pozostałych przypadkach użytkownik świadomie klika „BDB: Wykonaj”
→ Native Host wykonuje operację
→ BDB zwraca wynik
→ ChatGPT analizuje wynik
→ zmiana jest testowana
→ zmiana jest promowana
→ lokalny master jest synchronizowany z prywatnym main
→ użytkownik ręcznie weryfikuje GUI, gdy nie ma automatycznego testu interfejsu

Po aktualizacji plików rozszerzenia należy przeładować rozszerzenie na `chrome://extensions` i odświeżyć kartę ChatGPT. Panel powinien pokazywać wersję 0.4.3. Globalne AUTO pozostaje ustawieniem użytkownika i nie jest włączane przez launcher ani przez wznowienie zadania.
